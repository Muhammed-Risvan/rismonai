# Rismon.ai — Implementation Plan

> Status: **proposed plan for review** — not started. Reaches a usable release candidate
> for the Cloud Security Engineer journey. Consistent with `brief.md`, `user-flows.md`,
> `spec.md`. Built on the existing foundation (Next.js 16 / React 19 / TS / Supabase /
> Drizzle / Tailwind / Vitest). Each milestone is independently buildable, testable,
> reviewable, and recoverable.

**How to read this plan.**
- Milestones are ordered by dependency; each has a clear **completion condition**.
- "Shared interfaces first": M0–M1 define contracts (types, schemas, table shapes) so later
  UI/core/content work can proceed with confidence.
- Every milestone ends green on `pnpm lint`, `pnpm typecheck`, `pnpm test` (and, where the
  DB is touched, `pnpm test:db`).
- Migrations are generated by the agent (`pnpm db:generate`) but **applied by the human**
  after review (`pnpm db:migrate`), per `AGENTS.md`/`docs/development.md`.
- **Build note:** `pnpm build` needs Supabase env set (fails locally without `.env.local`);
  Vercel has env set. Verify build in an env-configured context.

**Milestone index:** M0 Foundations & contracts · M1 Learner data model · M2 Onboarding &
ambition · M3 Baseline diagnostic · M4 Curriculum content (CSE) · M5 Mastery engine ·
M6 Attempts & exercise grading · M7 Teaching interface · M8 Roadmap & planner · M9 Revision
& misconceptions · M10 AI adapter · M11 Practical projects · M12 Dashboard & 3D brain ·
M13 Data lifecycle (export/delete/reset) · M14 Hardening & a11y · M15 Release verification.

## M0 — Foundations, shared types & contracts

- **Objective:** establish the pure-core skeleton, shared TypeScript/Zod contracts, and the
  ambition catalog shape so all later work builds against stable interfaces.
- **Includes:** `src/core/` module layout; core domain types (`CapabilityId`, mastery
  states, `Attempt`, `Recommendation`); `content/` schema (TypeScript + Zod) for ambitions,
  competency maps, lessons, exercises, misconceptions; a content **DAG validator** (pure,
  tested: rejects cycles + dangling prerequisites).
- **Dependencies:** none (builds on existing repo).
- **Files/areas:** new `src/core/**`, `content/**`, `tests/core/**`, `content/**/*.test.ts`.
- **Tests:** DAG validator (valid graph, cycle, dangling ref); type-level contract checks.
- **Acceptance:** validator passes on a seed competency map; fails loudly on a cycle; all
  new modules pure (no DB/network/clock) — enforced by review + a lint-style test if practical.
- **Risks/decisions:** finalize the content schema shape early (changing it later is costly).
- **Completion condition:** seed Cloud Security Engineer competency map loads and validates;
  `pnpm test` green.

## M1 — Learner data model (schema + services + isolation)

- **Objective:** add persistence for the learning domain, backward-compatibly, with RLS and
  isolation, without disturbing existing tables/behavior.
- **Includes (additive migrations):** `ambitions` (catalog, seeded from `content/`),
  `goals.ambition_id` (nullable FK), `learner_capabilities` (capability state per learner),
  `attempts`, `misconceptions`, `onboarding_answers`, `roadmap_items`, `revision_items`,
  `projects` + `project_evidence`. All learner-scoped tables: RLS + `REVOKE ALL … FROM anon,
  authenticated` + `ON DELETE CASCADE` to the learner. Services + data-access + Zod at
  boundaries, mirroring existing `services/goals.ts` / `data/goals.ts`.
- **Dependencies:** M0 (types/contracts).
- **Files/areas:** `src/server/db/schema.ts`, `src/server/data/**`, `src/server/services/**`,
  `src/server/validation/**`, `drizzle/**` (generated), `tests/db-integration.test.ts`.
- **Tests:** DB-integration for each new table: persistence, cascade delete on user removal,
  and **two-account isolation** (learner A cannot read/write B's rows) — mirror existing
  throwaway-user pattern.
- **Acceptance:** existing dashboard + goals still work unchanged; new tables isolated;
  migrations reviewed by human before apply.
- **Risks/decisions:** confirm the single-active-goal invariant is kept for MVP (no migration
  now). Keep every new column additive/nullable.
- **Completion condition:** `pnpm test` + `pnpm test:db` green; human has reviewed & applied
  the migration.

## M2 — Onboarding & ambition selection

- **Objective:** capture ambition, intended outcome, SMART inputs, and background; store
  self-reported answers as a **hypothesis** (never mastery).
- **Includes:** ambition picker (CSE); clarification of `target_outcome`; SMART inputs
  (reuse `goals.deadline`, `hours_per_week`); adaptive background questions persisted to
  `onboarding_answers`; resumable; server derives goal status (reuse `createGoal`).
- **Dependencies:** M1 (tables), M0 (contracts).
- **Files/areas:** `src/app/(learning)/onboarding/**`, `src/server/services/onboarding.ts`,
  `src/server/validation/onboarding.ts`, tests.
- **Tests:** service unit tests (mocked auth); route 401s without session; onboarding
  answers persist + resume.
- **Acceptance:** a learner completes onboarding; answers persist across refresh; goal row
  created with server-chosen status; existing goal behavior unchanged.
- **Risks/decisions:** signup vs manual provisioning (M14 wires the chosen path; onboarding
  assumes an authenticated learner either way).
- **Completion condition:** onboarding end-to-end works for a test learner; tests green.

## M3 — Baseline diagnostic

- **Objective:** assess real starting capability (adaptive, deterministic), not self-report.
- **Includes:** adaptive item selection (pure core, in `src/core`); deterministic grading by
  answer keys; writes initial `learner_capabilities` levels; coverage gate; resume; explicit
  "start at beginner (record as unknown)" option.
- **Dependencies:** M1, M2, M4 (needs at least a starter set of diagnostic items).
- **Files/areas:** `src/core/diagnostic/**`, `src/server/services/diagnostic.ts`,
  `src/app/(learning)/diagnostic/**`, tests.
- **Tests:** pure selection logic (branching on answers); grading; coverage gate; resume;
  two-account isolation of results.
- **Acceptance:** a beginner and an experienced learner end with **different** capability
  levels from the same item bank; partial progress resumes.
- **Risks/decisions:** item-bank size vs. effort (start with a focused entry-level set).
- **Completion condition:** diagnostic produces differentiated starting state; tests green.

## M4 — Curriculum content: Cloud Security Engineer (first arc)

- **Objective:** author enough **reviewed** content for a coherent beginner→core arc, as
  versioned structured data.
- **Includes:** competency map (capabilities + prerequisite DAG); objectives; lessons
  (why-it-matters, analogy, visual, example); exercises with answer keys; known
  misconceptions (signature → remediation); assessment items; ≥1 guided project spec.
  Content carries `version` + `lastReviewed`.
- **Dependencies:** M0 (schema + validator).
- **Files/areas:** `content/cloud-security-engineer/**`, content tests.
- **Tests:** DAG validity; every exercise has an answer key; every misconception references a
  real capability; no dangling refs.
- **Acceptance:** a beginner can traverse a complete first arc (foundations → core concepts →
  project) with no missing prerequisites; content reviewed + signed off by owner.
- **Risks/decisions:** **curriculum depth** (owner confirms exact first-arc boundary); accuracy
  review cadence; content is hand-authored (never AI-invented).
- **Completion condition:** first arc complete, validated, and owner-reviewed.

## M5 — Evidence-based mastery engine (pure core)

- **Objective:** deterministic, explainable mastery from attempt evidence.
- **Includes:** mastery states (`unknown`,`untested`,`developing`,`mastered`,
  `revision-needed`); pure transition functions (**time injected**); assisted≠independent
  rule; explainability (why a level); no AI influence.
- **Dependencies:** M0 (types).
- **Files/areas:** `src/core/mastery/**`, `tests/core/mastery.test.ts`.
- **Tests:** exhaustive transitions; assisted never→`mastered`; independent pass→`mastered`;
  time injection (no clock); explainability output.
- **Acceptance:** mastery changes only from graded evidence; every state change is explainable
  and reproducible in tests.
- **Risks/decisions:** exact thresholds for `developing` vs `mastered` (define + test).
- **Completion condition:** core mastery module fully unit-tested; no DB/network/clock.

## M6 — Attempts & exercise grading (services + persistence)

- **Objective:** record every attempt and apply the mastery engine server-side.
- **Includes:** submit-answer service (validates via Zod; grades deterministically; records
  attempt with mode/hints; calls M5 to update capability; detects misconceptions); idempotent
  submission; routes for exercises/assessments.
- **Dependencies:** M1, M5, M4.
- **Files/areas:** `src/server/services/attempts.ts`, `src/server/data/attempts.ts`,
  `src/app/api/**` (learning), tests.
- **Tests:** grading correctness; assisted vs independent persistence; idempotency; isolation;
  mastery applied only via evidence.
- **Acceptance:** attempts persist across sessions; mastery updates only from recorded passes;
  AI is not in this path.
- **Risks/decisions:** attempt volume/storage; ensure indexes on learner-scoped queries.
- **Completion condition:** end-to-end attempt → grade → mastery works; DB + unit tests green.

## M7 — Teaching interface (lessons + exercises UI)

- **Objective:** a complete, mobile-friendly learning UI: one concept at a time.
- **Includes:** lesson view (why-it-matters, analogy, visual, example); guided exercise
  (hints) and independent challenge (no hints) using the existing design system; honest
  feedback; "explain differently / simpler example" affordance (deterministic fallback until
  M10); progress signal (viewing never sets mastery); accessible + responsive.
- **Dependencies:** M4, M6.
- **Files/areas:** `src/app/(learning)/learn/**`, `src/components/learning/**`, tests.
- **Tests:** component/route tests (mocked services); a11y smoke (labels, focus, aria-live
  for feedback); responsive rendering sanity.
- **Acceptance:** a learner reads a lesson and completes a guided + independent item; feedback
  is honest; nothing is marked mastered without an independent pass.
- **Risks/decisions:** keep interactions short; avoid a heavy client state layer (extract one
  only when justified).
- **Completion condition:** full lesson→exercise→challenge loop usable on desktop + phone.

## M8 — Roadmap & adaptive planner

- **Objective:** generate a personalized SMART roadmap and recommend the next activity with a
  reason.
- **Includes:** pure gap analysis + roadmap builder (pure core); pure planner (prerequisite
  readiness, weaknesses, due revision, ambition map, study time) returning a recommendation +
  reason; services + routes; roadmap persisted as `roadmap_items`.
- **Dependencies:** M0, M1, M3, M5.
- **Files/areas:** `src/core/planner/**`, `src/core/roadmap/**`, `src/server/services/planner.ts`,
  `src/app/(learning)/roadmap/**`, tests.
- **Tests:** two different starting states → different roadmaps (personalization proof);
  recommendation includes a reason; due revision prioritized; planner is AI-independent;
  "identical path" detection (warn if all learners would get the same plan).
- **Acceptance:** beginner vs experienced roadmaps visibly differ; next-activity has a reason;
  logic unit-tested without any provider.
- **Risks/decisions:** planner tuning; avoid over-fitting to a single content shape.
- **Completion condition:** personalized roadmap + reasoned next-activity work; tests green.

## M9 — Revision & misconception recovery

- **Objective:** resurface misunderstandings and strengthen fading skills.
- **Includes:** spaced-revision scheduler (pure core, time injected); misconception lifecycle
  (open → cleared by independent pass → re-record on repeat failure); revision surfaced before
  new content; UI for revision sessions.
- **Dependencies:** M5, M6, M8.
- **Files/areas:** `src/core/revision/**`, `src/server/services/revision.ts`,
  `src/app/(learning)/revision/**`, tests.
- **Tests:** scheduling with injected time; misconception clear/re-record; revision prioritized
  by planner; isolation.
- **Acceptance:** a misconception detected in practice reappears in revision and can be cleared
  by an independent pass.
- **Risks/decisions:** spacing intervals (start simple, tune later).
- **Completion condition:** revision loop works end-to-end; core scheduling tested.

## M10 — AI provider adapter (bounded, validated, fail-safe)

- **Objective:** add AI proposals without coupling, corrupting records, or touching mastery.
- **Provider (confirmed):** **OpenRouter** is the first planned provider — an API
  aggregator fronting many models behind one key + an OpenAI-compatible API. The adapter
  must still permit **additional providers/models** without coupling learning logic to one
  provider (task-oriented interface; core logic never calls a provider directly). Document
  alternatives (direct provider SDKs) and any dependency before adding it (per `AGENTS.md`).
- **Includes:** `src/server/ai/` adapter behind a small task-oriented interface (e.g.
  `explainConcept`, `suggestExample`, `reviewProject`); **secure API-key management**
  (server-only env, never logged); **model discovery** (list/select models via the API);
  **connection testing** (a health/ping path to verify the key + model before use);
  **task-based routing** (map each bounded task to an appropriate model); **usage controls**
  (per-request cost/time caps, rate limiting, circuit-breaker); **controlled fallback**
  (deterministic content when a task can't be served); Zod validation of all output;
  timeout/backoff for 429 & outages; wired only to bounded features (alt explanation, extra
  example, project feedback). Env via `AI_PROVIDER_API_KEY` (already reserved).
- **Dependencies:** M7 (surfaces), M6 (must not alter mastery path).
- **Files/areas:** `src/server/ai/**`, config, call sites in learning services/UI, tests with
  a fake provider.
- **Tests:** fake-provider success; malformed output discarded; timeout; 429; full outage →
  deterministic fallback; **assert mastery/answer keys unchanged by any AI path**; connection
  test + model discovery against a stubbed client.
- **Acceptance:** with the provider disabled, the app is fully usable; no AI output can set
  mastery or override keys; a second provider/model can be added without touching core logic;
  CSP planned if new client script ships.
- **Risks/decisions:** provider/model defaults + cost caps (owner); data-retention/privacy
  disclosure on privacy/terms (OpenRouter is a third party — describe before go-live).
- **Completion condition:** adapter passes all failure-mode tests; no mastery/key mutation.

## M11 — Practical projects & portfolio evidence

- **Objective:** let learners demonstrate integrated capability on a guided project.
- **Includes:** project runner (steps + deterministic acceptance criteria); learner records
  what they did + attaches evidence; optional AI *feedback* (validated, never marks complete);
  honest completion (shown complete only when criteria recorded as met).
- **Dependencies:** M4, M6, M7 (M10 optional for feedback).
- **Files/areas:** `src/app/(learning)/projects/**`, `src/server/services/projects.ts`,
  `src/server/data/projects.ts`, tests.
- **Tests:** completion gated by criteria; evidence persists; AI cannot mark complete; isolation.
- **Acceptance:** ≥1 CSE project completable with recorded evidence; never falsely shown complete.
- **Risks/decisions:** how strictly to verify project criteria (start with a confirm-checklist +
  any feasible automated checks).
- **Completion condition:** a project can be completed and evidenced; tests green.

## M12 — Dashboard, gamification & 3D brain data integration

- **Objective:** honest, meaningful visualization of real progress.
- **Includes:** dashboard shows active ambition, roadmap progress, real capability levels, due
  revision, reasoned next activity, completed projects; **3D brain learner-data mode** reads
  persisted mastery (regions brighten as capabilities master) while staying decorative with no
  data and preserving all performance/a11y rules; meaningful gamification tied to evidence
  (no rewards for mere activity).
- **Dependencies:** M5, M8, M9, M11.
- **Files/areas:** `src/app/dashboard/**` (extend, preserve existing profile/goals),
  `src/components/brain/**` (add data mode), `src/components/dashboard/**`, tests.
- **Tests:** dashboard renders only evidence-backed levels; brain data mode matches saved state;
  brain still decorative on `/`; no fake mastery.
- **Acceptance:** displayed progress exactly matches persisted evidence; brain reflects real data
  when present and is decorative otherwise.
- **Risks/decisions:** keep the existing dashboard working; add, don't rewrite. Brain data mapping
  must be clearly derived from real state.
- **Completion condition:** dashboard + brain accurate to saved data; existing dashboard features
  intact.

## M13 — Data lifecycle: export, deletion, (optional reset)

- **Objective:** learner owns their data.
- **Includes:** server-side **export** (learner-scoped, machine-readable) as a download;
  **account-data deletion** with re-confirmation (cascades all learner-scoped tables — verify);
  optional **reset progress** (scoped deletes, keeps account) if approved.
- **Dependencies:** M1 (all tables exist), M12.
- **Files/areas:** `src/app/(learning)/settings/**` or account routes,
  `src/server/services/data-lifecycle.ts`, `src/app/api/**`, tests.
- **Tests:** export contains only the authenticated learner's data; deletion cascades completely
  (verify via raw connection); reset (if in scope) clears progress but not profile/auth.
- **Acceptance:** export + deletion verified end-to-end; no residual learner rows after delete.
- **Risks/decisions:** **reset in MVP?** (owner); ensure cascade covers every new table.
- **Completion condition:** export + deletion verified; reset per decision.

## M14 — Hardening, auth path, a11y, CSP, docs

- **Objective:** production-grade safety and the chosen account path.
- **Includes:** wire **public signup** (`signUp` server action mirroring safe `signInAction`) **or**
  document **manual provisioning** (owner decision); add **Content-Security-Policy** (audit
  `unsafe-inline/eval` + Supabase origins; coordinate with WebGL/AI); accessibility pass across
  new UI (focus, aria-live, contrast, reduced-motion, keyboard); update **privacy/terms** (from
  DRAFT) to describe learning data, AI processing, retention; confirm rate-limiting posture.
- **Dependencies:** M2, M10, M12.
- **Files/areas:** `src/app/login/**` + new signup, `next.config.ts` (CSP), `src/app/privacy`,
  `src/app/terms`, a11y fixes across new components, tests.
- **Tests:** signup 401/validation parity; CSP present; a11y smoke tests; docs build.
- **Acceptance:** chosen auth path works; CSP set; privacy/terms accurately describe the product;
  a11y checks pass.
- **Risks/decisions:** **signup vs manual** (owner); CSP vs WebGL/Next inline needs (test build +
  a live page).
- **Completion condition:** auth path live; CSP + a11y verified; legal pages updated.

## M15 — Release verification (release candidate)

- **Objective:** prove the whole product meets the acceptance criteria in `spec.md` §20.
- **Includes:** full green suite (`pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:db`);
  production **`pnpm build`** in an env-configured context; an end-to-end **manual test script**
  (new learner → onboarding → diagnostic → personalized roadmap → learn → assess → mastery →
  revision → project → dashboard/brain → export → delete); **AI-outage drill**; two-account
  isolation check; a written **deploy/release verification runbook**; owner sign-off.
- **Dependencies:** all prior milestones.
- **Files/areas:** no app code required except fixes found; `docs/release-verification.md`
  (runbook).
- **Tests:** the full automated suite + the manual script executed and recorded.
- **Acceptance:** every `spec.md` §20 criterion demonstrably passes; runbook followed; owner
  approves.
- **Risks/decisions:** schedule the AI-outage + isolation drills explicitly; don't skip the
  manual end-to-end pass.
- **Completion condition:** release candidate verified end-to-end and signed off.

## Parallelization guidance

- **Contract-first:** M0 (types/schemas/DAG) must land before content (M4) and services
  (M1/M6).
- **Can proceed in parallel after M0+M1:** M4 (content), M5 (mastery core), and early M8 (core
  planner/roadmap) touch different areas and share only the M0 contracts.
- **UI (M7/M12) depends on** their services/core; build UI last within each vertical slice.
- **M10 (AI) is isolated** behind the adapter and can be developed against a fake provider in
  parallel, then wired in.
- Never parallelize two changes to the **same migration**; batch additive tables into one
  reviewed migration where sensible, or sequence them.

## Rollback / recovery

- Each milestone is additive and independently revertable (new files; additive migrations).
- Existing functionality (auth, profile, goals, dashboard, marketing) must keep working after
  every milestone; a regression here blocks the milestone.
